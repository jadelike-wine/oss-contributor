# 贡献控制器使用与恢复（2026-10-31）

本文说明当前代码行为。本轮工程验收结果与上游待观察事项见 [工程进度](conversion-progress-2026-10-31.md)，历史兼容证据见 [历史副本回放](conversion-history-replay-2026-10-31.md)。

## 授权与运行入口

`Pipeline` 默认 `allow_external_writes=False`。直接调用 `auto`、`tick`、`analyze` 等入口可以读取上游、调用配置的模型、修改本地隔离工作区、执行测试并保存材料，但不能推送远端或创建、修改 GitHub 内容。`automation.enabled`、仓库白名单及模型审查结果均不替代明确的发布授权。

只有已经明确授权相应远端操作时，才使用全局开关 `python -X utf8 contribute.py --allow-external-writes auto`。开关位于子命令之前；它只是执行条件，不是获得授权的方法。没有授权时保留本地材料和 `publication_hold=external_writes_disabled`，不要为了走完状态机开启外写。

2026-11-05 更新：用户已明确授权本项目持续定时发布，当前 `automation.scheduled_external_writes=true`。`hermes_tick.py` 每次启动读取该布尔值并传入 `--allow-external-writes tick`；缺省或 `false` 不传入，其他类型拒绝启动。开关修改从下次启动生效，所有仓库政策和补丁验证门禁继续生效。

```powershell
# 只读本地指标与研究记录，不触发数据库迁移
python -X utf8 contribute.py metrics --limit 10
python -X utf8 contribute.py candidates
python -X utf8 contribute.py matrix <任务ID>

# 不调用模型、不发布；可能进行只读网络健康核验和兼容初始化
python -X utf8 contribute.py auto --dry-run

# 默认无外部写入；会推进本地任务及模型研究
python -X utf8 contribute.py auto
python -X utf8 contribute.py tick

# 完整目录扫描，仍允许有效缓存命中
python -X utf8 contribute.py scan
```

`research-batch` 专门进行本地研究，不调用实现或发布入口。`catalog_sweep.py` 仍是单独的全目录采集/静态分诊入口，其恢复资料不等于已执行目标项目测试。

## 调度、预算与扫描

当前配置的实现任务上限为 8，维护上限为 6，研究候选上限为 3，均串行推进。同一任务在同一类额度中只计一次；PR 反馈需要改代码时还要取得实现名额。顺序优先实际 PR 反馈、待提交/验证/审查补丁、已复现任务、已通过研究的实现候选，再处理新研究。等待方向确认的功能提案不占据可实现候选的优先级。

任务额度不是模型总预算。当前仍为单轮 32 次模型入口调用、5,400 秒，单任务 40 次累计入口调用及本轮 1,800 秒，每日已记录运行时间 21,600 秒；本轮修复没有提高这些总额。自动研究开启时，默认从既有单轮预算内预留 `research.reserve_model_calls=2` 和 `research.reserve_seconds=600`。交付阶段用完其份额后让出剩余额度；研究仍受单任务、每日及总预算限制，预留不保证模型服务一定可用。

2026-11-06 吞吐优化：单轮研究候选从 8 减到 3，每个候选完成后立即尝试正常交付，避免等整批研究结束。研究结束后，剩余预算可恢复此前仅因研究预留而让出的任务，并继续尚未尝试的已有任务；失败和任务预算耗尽不因此重试。`yielded` 记录阶段让出，成功恢复后不会把整轮误标为预算耗尽。派发首先进行不占位的额度检查，额度已满时不再对该类别的整个候选队列发起政策预检；其他类别和已经占位的任务仍可继续。最终发布的实时政策、精确补丁验证及审查不变。

交付和研究有不同的持久游标。研究轮转覆盖研究准入池，包括不能自动贡献但允许研究的仓库。扫描另有持久游标：`tick` 先推进任务，再对完整目录最多实际采集 `scanning.repositories_per_tick=12` 个未命中缓存的仓库；单独 `scan` 没有这个数量上限。

`scanning.cache_seconds` 当前为 21,600 秒，`repository_checks.cache_seconds` 为 86,400 秒，旧配置缺省 0；将对应值设为 0 可关闭该类缓存。成功记录按原观察时间过期，缓存命中不延长有效期。失败记录不能冒充成功缓存，开始下一轮时先保留全部有效检查点，避免中断丢失未遍历的缓存。

`runs/scan-summary.json` 始终列出完整目录，区分 `scanned`、`cached`、`unknown`、`not_scanned` 和跳过项。检查 `completed` 和各类数量，不能把一次正常进程退出或命中缓存的仓库数解释为完整新扫描。Issue/PR 发布前实时核验目标仓库与贡献规则；PR 还检查 Issue 是否开放、竞争实现及精确补丁证据，不以扫描缓存放行。

2026-11-06 更新：扫描失败保留错误类别和累计尝试数，先冷却再有界重试。连续三次失败后转为低频恢复探测，默认冷却一小时、每轮最多探测一个耗尽仓库，其他仓库继续轮转。人工核验服务恢复后，也可执行 `python contribute.py scan --force` 单次绕过缓存及扫描冷却；错误与恢复事件保留，成功才清除当前故障状态。它不重置任务质量次数，也不授予发布权限。

每仓额外刷新少量旧 HOLD，并优先处理 `issue_refresh_queue` 中的历史复核请求。`python contribute.py rescan-issues owner/repo 123 456` 实时复核指定 Issue（最多 10 条），保留原拦截原因；未知关联继续保持未知。同仓明确 closing PR 仍阻止重复实现，跨仓同号不会关联，普通引用、测试专用和部分覆盖转入正常范围评审。

`python contribute.py register-pr --help` 列出已发布 PR 的维护恢复入口。先用完整 head/base 身份、原回归基线和干净工作区预览，再用 `--apply` 原子绑定；可提供当前验证计划，否则只观察。`--expected-base` 固定 PR 元数据快照，真实目标分支另行查询并保存 `target_base_sha`，绑定前再次核验。合并和发布均核验真实目标 tip，不把可能陈旧的 PR base 快照当作当前分支。不同或终态旧任务保留，新建维护任务不继承旧批准。维护阶段记录 head/base 变化和合并冲突，普通 merge 后重新走固定基线/补丁验证与审查，不强推。

## 内容身份与发布恢复

`tree-v2:<Git tree>` 表示 Git 实际会提交的内容，计算使用临时索引，不改用户真实暂存区。新增文件从未跟踪转为暂存、补丁已经提交或进程重启，只要最终内容相同，身份不变。文件内容、删除、可执行位、符号链接或 Git clean filter 后的内容变化会改变身份；未解决的索引冲突直接拒绝识别。

旧格式指纹无法安全换算。旧 `verification.json`、`approved_fingerprint` 或远端验证收据不能直接批准 `tree-v2` 内容。必须保留旧证据，重新完成固定基线失败、补丁同一测试通过、项目检查和审查。默认验证收据最长 24 小时，由 `automation.verification_max_age_seconds` 控制；过期、缺少时间戳或内容变化均要求重新验证和审查，而不是修改收据时间。

提交前持久化 `expected_tree`；`ensure_commit` 可以在提交成功但响应丢失后发现并采用已存在的正确提交，避免再生成一个提交。实际暂存、提交后和钩子运行后的内容都必须一致。Windows 的 npm/pnpm/Corepack 钩子通过正确引用的 Node 入口执行；路径修复不意味着可以跳过上游检查。

新建任务及验证基线 worktree 使用命令级 `core.autocrlf=false`、`core.eol=lf`，避免宿主机自动 CRLF 转换使 shebang 或 Markdown 测试出现假失败；仓库 `.gitattributes` 的显式行尾要求仍优先。不会更改共享或全局 Git 配置，也不会重写已有工作区。已有工作区若受此问题影响，应先在固定无补丁基线复现、备份原文件，再仅恢复已确认未修改的验证输入为上游原始字节，并保存前后哈希；不要混入补丁或批量覆盖用户改动。

推送先保存目标远端、分支和提交。`ensure_push` 在写入前后用 `ls-remote` 核对精确提交 SHA；推送报错只有在读请求证明同一提交已到达目标分支时才能恢复。普通推送被拒绝或远端状态不明就保留意图，不强推。

Issue/PR 创建前设置 `issue_create_pending` 或 `pr_create_pending`。响应丢失后，下一次先按保存的身份查询：Issue 使用作者与控制器标记，PR 使用保存的作者/分支；查询包含关闭状态，避免重复创建。

| 对账结果 | 后续动作 |
| --- | --- |
| 唯一匹配 | 恢复原编号，继续观察原发布 |
| 成功查询但零匹配 | 保留 pending，15 分钟后再只读查询；最多三次 |
| 三次仍无匹配 | `manual_verification`，停止自动查询与创建，等待人工核验 |
| 多个匹配 | 立即转人工核验，不能任取一个或再创建 |
| 网络/权限/解析失败 | 保持未知并记录故障，不把失败当作零匹配 |

人工核验应检查保存的 intent、所有开放/关闭发布、远端分支及原日志，记录结论和恢复位置。当前没有一键强制重发命令；不要删除 pending、清空失败次数或重建任务 ID 来绕过对账。

## 故障与质量问题

网络、限流、证书、服务不可用、模型 JSON/部分响应结构错误、超时分别记入基础设施失败。默认最多三次，初始冷却 300 秒，指数增加且每次最多 3,600 秒；任务耗尽后不会仅因时间过去自动重跑。这些失败不扣候选的质量尝试数，但已经启动的模型调用仍占实际调用预算。2026-11-06 起，安装步骤单列 `setup_error`，保留错误、执行方案和工具/依赖内容指纹，并有界重新规划；耗尽后的恢复必须有实质环境或安装方案变化，最多恢复一次。单纯更新时间戳或改测试不算环境修复。

证据不足和补丁错误继续使用质量尝试数；政策阻塞保留阶段，等待政策条件或证据变化。模型通道同轮两次传输/服务故障后跳过后续依赖该通道的模型阶段；本地复现/检查等不依赖模型的阶段仍可推进。该熔断不是换模型指令，也不关闭 TLS 校验。

研究响应的单一格式恢复：只有 Hermes 正常完成、无工具/错误事件、流式文本与最终文本完全一致，且 JSON 仅缺最外层最后一个 `}` 时，才补全该符号并保存原始文本、哈希和恢复收据。不补字段、不改变值，不增加模型调用。研究结构、固定源码引文、政策及查重检查照常执行；审查批准不使用此恢复。其他截断、歧义、重复键和非有限数字继续拒绝，研究纠正次数不增加。

检查每个任务的 `failure_category`、`infrastructure_failures`、`attempts`、`stop_reason` 和原日志。服务恢复只能说明可以考虑重试，不能证明补丁正确。耗尽后须先查明原因；当前没有自动把 `FAILED` 任务或耗尽计数清零的恢复入口。

## 数据库、重复任务与中断

1. 先检查 Git 状态、控制器、子进程和锁，保留已有修改、工作区和日志。不要与仍运行的控制器同时改同一任务。
2. 分析时通过 SQLite backup API 获取一致性快照，不能只复制可能仍有 WAL 数据的主文件。例如 `python -X utf8 audit_conversion.py --source state/tasks.db --output runs/<新的审计目录>` 只建立本地快照和审计结果。
3. 修改生产状态前重新备份并确保独占。迁移增加表或列，保留旧数据；重复执行后检查 `PRAGMA integrity_check`，并核对历史表行数与哈希。
4. 对 `running` 先核验 `runs.owner_pid`、锁中的父 PID 和子 PID。任一仍活着就不恢复。旧版无 owner PID 的行默认不自动恢复；只有完成进程核验后才向 `telemetry.recover_interrupted` 显式传入 `legacy_processes_checked=True`。
5. 恢复仅把遥测结束为 `interrupted`，保存原因和原任务阶段。耗时保留最后检查点，不把中断到恢复的时间补作执行时长。`recover_locks` 同样仅清理已停止父/子进程的锁；手工 `unlock --process-stopped` 参数不替代操作前的进程核验。

`replay_conversion.py --output <新的回放目录>` 可以在真实快照的新副本上验证两次迁移、两次恢复、历史哈希和完整队列排序。脚本拒绝覆盖已有副本；其旧新阶段派发比较替换了实际阶段正文，必须标为历史回放/模拟调度。

同一规范仓库和 Issue 的旧任务保留原记录，通过 `task_aliases` 关联到规范任务。新的扫描复用规范任务；存在独立 PR 的旧任务仍维护原 PR。相同调查主题的周标签被忽略，复用已有研究，不通过删除记录去重。研究审查还接收同仓库最多二十条历史候选，按实际需求和实现范围复核语义重复；仅可引用已提供任务，拒绝后保存原任务引用和审查材料，不删除历史。不同主题或不同 feature key 仍可能漏检，不能声称身份哈希解决了语义去重。

日历、等待时间和无关 SHA 更新不是重新研究的理由。重评需要完整采集的相关源码、规则、需求或竞争实现变化，并在日志中写明新证据与旧结论的关系；失败采集不能据此宣布功能缺失。当前不会仅凭新一周自动重置已完成或失败研究。

## 验证与上游结果分别报告

- **模拟测试**：临时 Git/bare remote、模拟模型/GitHub，验证状态机、故障和幂等机制。模拟 PR 不算提交。
- **历史回放**：完整真实数据库副本验证兼容、恢复、队列和重复工作；替换阶段正文的派发数量不算实际修复吞吐。
- **真实运行**：记录真实仓库、固定 SHA、网络/模型调用、基线断言失败、补丁通过及项目检查。无外写授权时明确禁止写入，并保留待提交材料。

补丁验证、模型审查、CI 等待批准、CI 失败、人类回应、明确方向同意、正式 PR 批准、合并与关闭分别记录。CI 按精确 PR head SHA 观察；`ACTION_REQUIRED` 是等待批准。同模型不同调用/通道不能叫独立模型审查。维护已有 PR 只响应内容变化，不重复催促。

本地验证或模型审查通过不代表维护者接受；历史回放中派发额度变大也不证明合并率提高。真实运行样本、有效实现任务、验证通过补丁和失败域需按相同范围比较，嵌套阶段耗时使用区间并集；上游回应、批准和合并继续作为单独的长期观察结果。
